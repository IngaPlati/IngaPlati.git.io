Term 2 reflections

Written in term 2 about building my CV in Markdown, embedding the video and publishing on GitHub Pages. The wording is unchanged; this site is the same portfolio rebuilt in HTML, CSS and JavaScript.

SSituation
I was required to create my CV using Markdown for the first time as part of my digital portfolio. I was used to using Microsoft Word, where formatting is visual and immediate, so working in a plain-text environment was unfamiliar.
TTask
My task was to structure and format a professional CV using Markdown that would be clear, readable, and suitable for publishing online.
AAction
I learned basic Markdown syntax such as headings, bullet points, and text formatting. I struggled with spacing, line breaks, and maintaining a consistent layout because Markdown does not provide full control over design like Word. Small mistakes in syntax sometimes caused formatting issues, and it was not always obvious what went wrong.

To overcome this, I used trial and error, repeatedly previewing my work and adjusting the syntax. I also simplified my layout to match what Markdown can handle instead of forcing complex formatting.
RResult
I successfully created a clean and structured CV. I improved my understanding of how developers format content for the web and developed stronger attention to detail. This experience also improved my ability to troubleshoot and adapt to new tools.

SSituation
After completing my CV, I needed to embed a mock interview video into the document using Markdown or HTML.
TTask
My task was to ensure that the video could be viewed directly within my CV when accessed online.
AAction
I initially tried to use Markdown but realised it does not support video embedding. I then used HTML video tags to insert the video. I struggled with getting the video to display correctly, especially with file paths and ensuring the format was supported.

I tested the video multiple times and corrected errors such as incorrect file references. This process required patience and careful checking of my code.
RResult
I successfully embedded the video into my CV. This helped me understand how Markdown can be extended using HTML and improved my ability to debug and fix technical issues.

SSituation
After completing my CV and embedding the video, I needed to publish my portfolio using GitHub Pages, which I had never used before.
TTask
My task was to deploy my CV as a live website and ensure everything displayed correctly online.
AAction
I enabled GitHub Pages in my repository settings and selected the correct branch. I found the process confusing at first, especially when my changes did not immediately appear on the live site.

I realised that I needed to commit and push my changes properly and wait for deployment. I also ensured my files were correctly structured and named.
RResult
I successfully published my CV as a live website. This experience helped me understand how hosting and deployment work. I also learned the importance of following correct processes and being patient when working with web technologies.

This project was both challenging and valuable. I struggled most with adjusting to a text-based formatting system, understanding the limitations of Markdown, and troubleshooting errors that were not always clear.

However, these challenges helped me develop problem-solving skills, attention to detail, and confidence in learning new technologies. I now have a better understanding of how to create, format, and publish web content.

Overall, this experience has prepared me for future projects in software and web development, and I feel more confident using tools like GitHub and Markdown to present my work professionally.

Agile Team Charter

A living social contract the team agrees on: why we exist, what we value, how we work and what is off limits (CPUT, 2026).

Download the charter (PDF)

Evidence

Version 1.1 of the charter was signed by all five team members on 21 October 2026. Version 1.0 was agreed at a team meeting that was moved from 10:30 to 14:30 at Mpho’s request. The content follows the CivicFix project documentation (Team Transformers, 2026a) and the assessment brief (CPUT, 2026). The PDF holds the full signed charter.

Shared purpose

Help residents report municipal hazards with one photo, and help the city turn each report into a verified, prioritised ticket that reaches the right department.

Team goal for the programme: a working, responsibly built prototype that we can demonstrate and defend.

Core values

  • Honesty. We label the demo as a demo and never claim the AI does what it does not yet do.
  • Responsibility. Public safety, privacy (POPIA) and human review come before speed.
  • Respect. Every member’s skill and time matters; we give feedback on the work, not the person.
  • Ownership. We say what we will do and we do it or say early that we cannot.

Boundaries

  • Nobody commits straight to the main branch without a team member knowing.
  • No real personal data, passwords or keys in the repository.
  • We do not present the demo as an official City or emergency service.
  • Individual work in marked assessments stays individual.

CommunicationThe Teams channel “Transformers” and a WhatsApp group for quick updates. Questions get an answer within the working day. Decisions are written down so nobody relies on memory.
Work trackingEvery task has an owner, agreed at the stand-up. A task counts as Done only when it meets the Definition of Done below. The sprint is also recorded on a Trello board.
Definition of DoneWorks on a teammate’s machine, is pushed to GitHub with a clear commit message, passes its UAT, and the owner has told the group.
Code and GitSmall commits, clear messages, pull before you push, tell the group before changing shared files. Resolve Git conflicts together, not silently.
DecisionsWe try to reach agreement. If we cannot, the group leader makes the call after hearing everyone, and the reason is recorded.
Conflict and workloadRaise problems early and privately first. If someone is overloaded or blocked, the team redistributes work in the next check-in.
Quality and safetyFollow the safety rules in the project documentation: confidence threshold of about 70%, human review of unsure cases, logged overrides, privacy by design.

SSituation
At the start of the CivicFix project I was the group leader of Team Transformers, five people building one prototype. Our earlier project, AgriBot, had shown two weak points: meetings that were not consistent and Git conflicts.
TTask
My task was to help the team agree how we would work, so that those problems would not return.
AAction
I led the discussion on our purpose, roles, a daily 09:30 stand-up, communication on Teams and WhatsApp, Git rules, the Definition of Done, boundaries and risks. We based the structure on the Scrum Guide (Schwaber and Sutherland, 2020) and the CivicFix project documentation (Team Transformers, 2026a). All five members signed version 1.1 on 21 October 2026.
RResult
The team had one shared set of rules and the daily stand-up became our fixed routine. When blockers appeared (absence, connectivity and backend readiness), the charter already listed them as risks with a response. In my own view the charter helped most with accountability: each task had an owner. Next time I would review it after the first week and have it signed earlier.

SSituation
The frontend developer, the backend developer and the tester each needed requirements they could build and test from. The CivicFix documentation listed 14 functional requirements and 13 acceptance tests (Team Transformers, 2026a).
TTask
My task was to turn those requirements into user stories with acceptance criteria and tasks.
AAction
I wrote 11 stories in the format “As a [user], I want [goal], so that [benefit]” (Cohn, 2004) for residents, dispatchers, field crews, department managers, reviewers, community members and the group leader. Every story links to a requirement and a test, so we can check that something is done instead of arguing about it. Writing from the user’s point of view showed me why each requirement exists. The AI and database stories were the hardest to size because they depended on the backend. Next time I would split large stories earlier.

Reflection (STAR)

Use + and − to open or close.

SSituation
There was more work than time. The Product Backlog list on Trello holds the first 11 cards, and the build work still needed a clear order. Some features already worked in the demo, but live image classification and the database were not connected.
TTask
My task was to rank the work so the team knew what mattered most.
AAction
I used MoSCoW (Clegg and Barker, 1994), which sorts work into Must, Should, Could and Won’t. The unfinished must-haves came first: live image AI, human review of uncertain results, the database, model evaluation and testing. I marked each item Demo built, Planned or Not planned using the progress table in the project documentation (Team Transformers, 2026a). The story points are proposals for the team to confirm.
RResult
The top of the backlog is now the work that makes CivicFix useful and safe, not the screens that already look finished. Connecting to real municipal systems sits at Won’t because it was outside our scope. This ranking became the list of improvements the team is working on now.
